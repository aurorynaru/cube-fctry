# Milestone B1 — local asset registry

`python tool/registry.py validate` replays `registry/events.jsonl` and checks all live project references. An empty journal is valid. `python tool/registry.py record ACTION --id ASSET_ID --actor ACTOR_ID --data payload.json --dry-run` validates a prospective event without appending it. Remove `--dry-run` to append. Both commands return exit code 0 on PASS and 1 on FAIL. JSON input files can be anywhere readable; **references inside them must be project-relative and restricted as below**. No actual game/actor approvals or asset imports are preloaded here.

## Configuration and data

1. Create `art/games/<game-id>.json`: `{"game_id":"<game-id>","actors":{"creators":["..."],"art_owners":["..."],"qc_reviewers":["..."],"importers":["..."],"final_reviewers":["..."]},"art_bibles":[...]}`. All roster lists must be nonempty. An Art Bible entry has **exactly** `version`, `path`, `sha256`, `profile_id`, `approval_evidence`, `approval_evidence_sha256`, `approved_by`, `approved_on`. The approver belongs to `art_owners`. Keep each approved version and its evidence at a stable path. This is operator-supplied evidence; the CLI cannot authenticate a human.
2. Put the game-specific Bible under `art/games/`. Its text includes `**Game ID:** <game-id>`, `**Style profile:** <profile-id>` and `**Version:** <version>`. Put a corresponding approval JSON in `registry/evidence/` with exactly `game_id`, `version`, `bible_sha256`, `profile_id`, `approved_by`, `approved_on`. The manifest pins hashes for both files. A profile must exist under exactly one of `art/presets/<id>.json` or `art/profiles/<id>.json` and satisfy the unchanged v1.0 profile schema.
3. Submit a v1.0 `asset-request.schema.json` **draft** inside `{"request":{...}}` for `create`. It must use the same ID, all pending gates, no deliverable hash, and no approval claims. For `rework`, submit a fresh draft with the same ID and game. The previous rejected candidate stays in the journal; its output and evidence remain subject to validation. Do not overwrite old candidate files.

The engine does not accept a status field as an operation. Valid operations are `create` (draft), then `art_approved`, `generated`, `qc_pending`, `qc_passed`, `imported`, `approved` in that exact order. `rejected` is available from any nonterminal stage with `{"reason":"...","evidence":["registry/evidence/..."]}`; the QC reviewer signs before import and a final reviewer signs after import. Only `rework` can follow rejection, returning to a new draft revision. Approved is terminal. The actor must be on the corresponding game's role roster, and the creator cannot QC, reject, or finally approve their own candidate.

| Operation | `--data` object (exact keys) | Required proof |
| --- | --- | --- |
| `art_approved` | `bible_version`, `bible_sha256`, `approval_evidence_sha256` | Selected game/profile-specific Bible and signed approval evidence match live hashes and manifest; art owner actor. |
| `generated` | `path`, `sha256`, `size_bytes`; plus `workflow_path`, `workflow_sha256` for `local_ai` | File exists, is nonempty, has expected extension/size/hash. Local AI requests contain model, workflow path and seed; workflow file hash matches. Creator actor. Other methods retain v1.0 generation/provenance fields. |
| `qc_pending` | Empty object `{}` | Previous generation must validate. |
| `qc_passed` | `gates`, `preimport_performance` | `gates` contains all six pre-import gate names (`originality`, `rights`, `style`, `technical`, `performance`, `tiling`), each with v1.0 gate structure. All required gates pass with nonempty evidence and authorized QC reviewer; optional tiling can be N/A. `preimport_performance` has `kind: "estimate"`, `notes`, `evidence`. QC actor signs off. |
| `imported` | `roblox_asset_id`, `record_path`, `record_sha256` | Positive decimal ID and pinned JSON record in `registry/evidence/`, exactly `game_id`, `asset_id`, `revision`, `output_sha256`, `roblox_asset_id`, `imported_by`, `imported_on`. Importer actor; no duplicate Roblox ID. |
| `approved` | `in_engine`, `measured_performance`, `final_evidence` | In-engine gate passes with evidence and final reviewer. Measured performance has `kind: "in_engine_measurement"`, `device`, `scene`, positive `fps`, `evidence`; final evidence nonempty. Final reviewer actor signs off. The pre-import estimate and in-engine measurement are distinct records. |

`in_engine` remains pending until `approved`. The original v1.0 schema still governs request structure; runtime replay adds cross-file/stage checks. The journal derives current approval status, deliverable hash, import ID and review records from events. Each event stores actor, timestamp, data, evidence-file hashes, previous event hash and its own hash. Validation checks the chain and every referenced file on every replay. All asset IDs are globally unique. All file references are relative POSIX paths without `.`/`..` or symlink escapes. Outputs are allowed under `outputs/` or `workflows/`; workflow files under `workflows/`; profiles and Bibles under `art/`; evidence under `registry/evidence/`. Inputs can be placed elsewhere, but references cannot escape the project.

Writes use an exclusive `registry/events.lock` created atomically. Simultaneous reads and writes fail closed. If a process crashes and leaves a lock, inspect journal integrity and any incomplete last line before manually removing the lock; do not remove a live writer's lock. A partial journal line or broken hash chain fails validation. A dry-run briefly acquires/releases the same lock but writes no event.

## Trust boundary and compatibility

The registry is a local audit and validation engine, not proof of identity or a Roblox API attestation. A person with project write access can fabricate roster entries/evidence/import JSON or rewrite and rehash the entire journal. Therefore an `imported` or `approved` status here is conditional on genuine operator-supplied evidence; the CLI cannot independently confirm the ID exists on Roblox, that screenshots came from Studio, licenses are genuine, or target-device FPS was measured honestly. Require independent human/platform review before treating records as real-world approvals. Do not enter synthetic fixture actors, imports, or evidence into the live registry.

Milestone A schemas stay **v1.0**, with no migration. Run `python tool/validate_art.py` and `python -m unittest discover -s tests -p 'test_*.py' -v` for reproducible schema and transition reports. The test suite builds temporary synthetic game/evidence files only; it creates no project asset approval.
