## 3. Exact contracts: validation, conditional trust and missing implementations

Python `Protocol` declarations express obligations; structural typing does not
authenticate an implementation. Construction/injection is a trusted deployment
responsibility. There is no default approving verifier or production adapter.

### 3.1 Independent approval and withdrawal — D3

`ApprovalVerifier.validate(evidence, binding) -> VerifiedApproval` must:

- Authenticate an event from an independently provisioned operator principal,
  channel and verification root, outside model-exposed tool arguments and
  agent-writable records. Verify issuance authenticity, event uniqueness, schema,
  issuer/actor/channel and current withdrawal-channel health/status.
- Validate exact observation/session, immutable action and target identity digests,
  discovery checkpoint, policy/deployment/catalog/runtime scope and evidence
  destination. Resolve the policy reference to exact operations/order, one attempt,
  lifecycle/control/teardown scope, budgets and limits. An opaque digest alone does
  not perform that policy validation.
- Validate approved/not-before/expiry claims and reject missing, forged, altered,
  wrong-scope, stale/unknown, withdrawn or channel-lost evidence. Return the exact
  evidence digest; never accept a model string, boolean, generic permission prompt
  or R9 TEST-ONLY continuation as authority.

The caller may conditionally trust the returned claims **only with a qualified
independent verifier/deployment**. The gate additionally checks evidence hash,
exact binding, nonempty issuer/approval ID/actor/channel, integer time claims and
`approved <= not_before < expires`; it compares the complete initial/final claims.
Approval times alone do not establish that current time is trustworthy.

`dispatch_guard(approval)` must serialize authenticated withdrawal acknowledgment
with the gate's final revalidation and simulated first byte. A withdrawal
acknowledged before that transition prevents it. Unknown/channel-lost status
refuses. The fake implements this with an `RLock` shared by `validate`, `withdraw`
and the dispatch guard. A separate thread can request withdrawal during the guard,
but cannot acknowledge it until that transition releases the lock. This is a
linearization rule, not instantaneous distributed revocation or remote cancellation.

**Unimplemented:** actual independent human channel, issuance/signatures/root/key
provisioning, event freshness protocol, protected verifier state/code, real policy
resolution, live post-discovery continuation and channel-loss monitoring. Fakes
recognize a fixed opaque lookup key; knowledge of it proves nothing outside tests.

### 3.2 Trusted time from two independent inputs — D4

`TimeEvidenceVerifier.validate(raw) -> SourceInterval` is the source-authentication
contract. It must authenticate an operator-supplied source and provenance, establish
the source's genuine independence domain, verify capture/generation semantics,
precision/error/transit/drift bounds and map evidence conservatively to a **common
local monotonic anchor** in the current boot/process/monitor epoch. Reject missing
bounds, copied unsigned time, unauthenticated inputs and shared-clock aliases.
Labels alone do not establish independence. Acquisition is outside this interface;
verification must not query a service or invent a missing source.

`TrustedTimeVerifier.verify((raw_a, raw_b), sample) -> TimeWindow` is implemented
by `TwoSourceTimeVerifier` over that injected source verifier. It requires:

1. Exactly two bounded nonempty byte inputs; source evidence hashes match inputs.
2. Distinct source IDs **and** independently verified independence domains.
3. Valid integer ordered bounds, the same anchor and current monitor epoch.
4. Healthy continuity, nonnegative elapsed monotonic time within explicit age limits.
5. Overlapping source intervals; disagreement fails closed.
6. The covering interval, **not** intersection or average, advanced outward by elapsed
   time and `ceil(elapsed * drift_ppb / 1e9)` on each side; refuse excessive width.

At each gate validation the whole current interval must start at/after approval/
not-before, and `upper + full_operation_budget + margin < expires`. Equality refuses.
An absolute monotonic deadline is established before persistence and never reset.
The final sample must precede it, preserve epoch and not regress from the initial
sample. Time evidence is reverified after storage, immediately before the inert
transition. The interval check conservatively reserves a full budget even then.

`LocalMonitor.sample()` must substantiate continuity and epoch/health, detecting
steps, reboot, suspend/resume, lost samples and timer uncertainty. A local monotonic
clock or formatted local UTC value is not an independent UTC source.

**Conditional trust:** interval arithmetic is implemented; source authentication,
normalization/capture-bracket mathematics and healthy monitoring are obligations
of the injected implementations. No R11 value is authenticated UTC. Test limits
(e.g. budget 30 ns, margin 2 ns, maximum age 200 ns, width 20 ns, drift 1,000,000 ppb)
exercise boundaries only; they are not measured platform bounds, approved R8
values or real time-service parameters.

**Unimplemented:** actual two-source selection/acquisition/authentication,
independence proof, calibrated capture/error/drift evidence, platform continuity
monitor, qualified policy budgets and independent post-observation UTC comparison.
No real time service is queried and no wall clock is changed.

### 3.3 One-use consumption — D3/D5

`ConsumptionStore.consume(approval, attempt) -> Consumption` must atomically admit
one winner for `(issuer, approval_id)` **across action bindings, sessions, concurrent
controllers and restarts**, with the spent intent committed/readback-verified before
any possible byte. The acknowledgment binds that key, complete binding digest and
attempt identity. Wrong acknowledgment refuses. Never release a spent attempt on
withdrawal, failure, timeout, ambiguous acknowledgment or crash; sacrifice
availability. Unknown/incomplete records remain quarantined/spent, with no rollback,
lease reset, automatic recovery, retry or restore-to-unspent.

The caller may trust a successful acknowledgment only with a qualified protected,
durable linearizable adapter. An exception is terminal, not permission to try again.
The fake uses a lock and dictionary and deliberately marks spent before its
uncertainty/crash injector fires. Tests reconstruct a gate with the **same surviving
fake store object**; they do not demonstrate process-restart or power-loss durability.
Discarding that object loses its replay state. The existing mutation authorization
store is not reused or promoted into a human authority.

**Unimplemented:** durable protected replay backend, cross-process locking,
transaction/recovery/backup semantics, tamper/rollback resistance, operator ownership
and production consumption. No production approval is issued or consumed.

### 3.4 Protected evidence/checkpoint store — D2/D5

`ProtectedEvidenceStore` has three operations:

- `prepare(attempt, action, prerequisite_digests)`: verify complete checkpoint/
  originals and policy binding, storage protection/health and reservations; persist
  the exact intended bytes, evidence digests and candidate intent new-only, with
  checked full write/flush/readback; return SHA-256.
- `verify(attempt, action, intent_digest)`: reread/recheck originals/checkpoint,
  intent, binding and storage prerequisites after slow work and before final checks.
- `record(attempt, decision)`: append a new-only candidate, denial or outcome with
  verified readback and its digest. Candidate and final outcome are distinct records;
  a candidate never means dispatch or completed observation. Invalid/missing digest
  acknowledgment is not success.

The caller may trust verified originals/records only under the qualified protected
storage deployment. The fake stores bytes and expected checkpoint/binding in memory;
hash checking demonstrates local consistency, not ACLs, durable originals or
authenticity against an agent/other writer. It does not implement R9's real temporary
file checkpoint machinery, nor change R7's evidence verifier to accept live records.

Production requirements represented **only as a contract**:

- Operator-named NTFS parent/volume, owners, readers/writers and effective inherited/
  explicit ACLs on ancestors/new leaves; agent/child cannot modify trusted code,
  namespace, authority, replay state or originals.
- Verified exclusive trusted writer/controlled ancestors, or handle-relative
  no-follow protection if exclusive namespace control cannot be established.
- Approved per-category/session/campaign logical accounting including duplicate and
  partial records; physical quota/allocation and finalization headroom reservation,
  not a free-space sample or a hash. No automatic deletion to regain authority.
- Confidential originals, separately approved redacted sharing/backups; retention
  **at least 30 days and until review completion, whichever is later**.
- Named recovery owner, specified durability/fault model, checked full writes,
  flush/fsync/readback; detect missing/torn/replaced records and preserve partial
  attempts. Never reconstruct success, overwrite or resume an uncertain observation.

No production ACL, filesystem namespace, quota, retention or evidence store was
modified. No universal power-loss persistence or hostile same-user resistance is
claimed. R8's oversized-retention/accounting amendment remains pending under D2.

## 4. The single vertical slice and its evidence order

1. `prepare_action` snapshots explicit synthetic target/details into canonical
   immutable bytes (bounded 4,096 bytes). Its fixed operation is
   `synthetic.read_only`. Bind action/target SHA-256, observation/session,
   checkpoint/policy hashes and evidence destination reference. No live target
   identity is defaulted from R7/R9 history.
2. Admit one caller through a nonblocking controller lock and mark this gate
   terminal for subsequent calls. Missing/invalid approval or current withdrawal
   status fails before intent consumption or bytes.
3. Verify both injected time inputs, interval/not-before/expiry/full budget; set
   the unresettable absolute attempt deadline before potentially slow storage.
4. Prepare/verify candidate intent with exact bytes and prerequisite digests.
5. Atomically spend approval in the injected one-use store and validate its
   acknowledgment. Any uncertainty is terminal and remains spent in the fake.
6. Append/read back a **spent candidate, not dispatch permission** before final
   checks. If that record cannot be stored, dispatch zero bytes.
7. Enter the withdrawal/dispatch guard; reverify evidence/checkpoint/intent and
   unchanged action; revalidate identical approval and current status; sample
   continuity/deadline and reverify time/expiry. After these final checks there
   is no disk operation or unguarded queue before the sole in-memory append.
8. Append one synthetic envelope to the inert sink, release the guard, and append
   a final outcome linking binding, approval/time hashes, intervals, intent and
   candidate digest. Return success only after the outcome's digest acknowledgment.

`OfflineResult.completed` means this fake flow completed with a recorded outcome.
`dispatched` reports actual **per-attempt simulated bytes > 0**, separately from
completion. A post-append evidence failure returns `completed=false`, no fabricated
receipt, and the real nonzero simulated byte count; it cannot retract those bytes.
Admission/authorization denials dispatch **zero bytes**. Repeating a terminal gate
reports zero new bytes even if an earlier successful invocation collected bytes.

A concurrent caller on the same busy controller is not admitted or queued: it
receives immediate `concurrent_attempt` with zero bytes and **no persisted receipt
claimed**. Separate controllers race the shared consumption store and only one
may append. Failure records are best effort if the evidence adapter itself fails;
absence of a receipt is explicit, never substituted with a success marker.

This is not a real partial-write implementation or hard scheduling deadline.
Actual dispatch/launch/resume, every remaining partial-write guard, in-flight abort/
owned-tree stop and independent post-time validation remain later integration work.
Revocation cannot unsend remote bytes. The existing strict frontend/contained
recorder retain their original guards; the R11 sink cannot contact them.

  intent persistence, altered approval and final time authentication/freshness/
  expiry rechecks; threaded acknowledgment before and during the final guard.
- Changed action before/after storage, changed target/details, missing/changed
  checkpoint, intent tampering, lost storage health, prepare/candidate/outcome write
  failures and invalid digest acknowledgments.
- Terminal/same-key/new-session replay, ambiguous consumption, wrong acknowledgment,
  simulated crash after spend, two-controller atomic consumption race and same-gate
  nonqueued concurrent refusal. Every pre-byte denial asserts zero collected bytes.
