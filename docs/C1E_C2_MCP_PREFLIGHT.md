## 5. Response-handling procedure

1. Retain the raw complete tool response and exact request before interpretation; record tool/server identity/version if supplied, UTC start/end, bytes, call ID, errors/truncation and applicable approval reference. Do not fabricate missing metadata. List discovery is inspected against its documented ID/name semantics; there is no discovery decoder in the adapter and no invented exact list envelope in C2A.
2. `read_studio_state()` returns a shallow raw mapping; despite its docstring wording, it does **not** decode or verify identity. `read_verified_identity()` applies `decode_mcp_payload()` then `verify_state_payload()`. Do not treat a successful raw read as verification.
3. `decode_mcp_payload()` accepts a direct mapping (internal fixture contract) or exactly `{"content":[{"type":"text","text":"<JSON>"}]}`. Unknown `result`/`error` wrappers, extra wrapper/block keys, non-text/multiple blocks and invalid JSON fail closed. Do not strip fences, scrape prose, concatenate blocks or unwrap guessed nesting. Direct mappings still need downstream exact schema validation; their acceptance alone is not a known-envelope verdict.
4. C2A tightens JSON text parsing: duplicate keys at any depth, NaN/Infinity and exponent overflow are rejected before identity validation. This adds no accepted envelopes. Duplicate keys already collapsed by an upstream mapping cannot be detected here; retain raw bytes and require a non-lossy transport before live acceptance. The parser still has no transport byte/depth guard; external collection bounds and a future bounded decoder are required before enabling live use.
5. `verify_state_payload()` requires exactly `studio_id`, `mode`, `place`, `user`, `team_create`; place exactly `name/place_id/game_id/creator_id/creator_type/is_unsaved`; user exactly `id/name`. Compare against operator-confirmed expectations. Missing server identity must never be populated from request arguments, fixtures or history. If real state exposes mode only, stop after step 2; that is an informative incompatibility finding, not permission to execute extra Luau.
6. Only after all execution gates: decode the hierarchy, first verify independently observed same-read identity (§6), then `normalize_snapshot_payload()`, then unchanged `validate_snapshot()`. Normalization requires exact snapshot/enumeration keys, complete/untruncated inventory, no duplicate paths, finite camera data, consistent summaries/tags. Harness validation checks parent/name/child/reachability consistency. No output is accepted as a trusted snapshot on any failure. Current code lacks the same-read stage, so this full live procedure is **not implemented**.
7. Unknown/malformed/oversize/truncated response or unknown behavior: preserve evidence with a refusal reason; stop all calls. Map any actual new shape offline in a later reviewed patch with a provenance-labeled fixture and negative tests. Do not patch and immediately retry within C2B approval. Never label synthetic tests as live compatibility evidence.

## 6. Target-identity continuity — design and blocker

Current behavior: state is verified, then hierarchy is read in a separate call. Both requests carry the configured Studio ID. Hierarchy contains **no** Studio, place, creator, user, document/session or mode identity. `normalize_snapshot_payload()` stamps the earlier verified state into `snapshot.studio`; `validate_snapshot()` cannot establish origin. The new synthetic characterization test explicitly demonstrates this gap. A caller-supplied echo would not fix it.

Minimum proposed solution, **not implemented or verified**:

1. Discovery/state must expose a trusted proxy/Studio-derived instance identity and a stable per-open-DataModel/session token (not a client parameter), along with independently read place identity. Bind the observation to the exact tool result/request routing metadata, not just an echoed request field.
2. In the same non-yielding bounded query that returns hierarchy, read actual `game.Name`, `game.PlaceId`, `game.GameId`, `game.CreatorId`, `game.CreatorType`, signed-in user via StudioService, and actual Edit status via an appropriate RunService observation; read again at end and require equality. Missing APIs/permissions fail closed. These are a design proposal, not newly reviewed executable Luau. Unsaved/Team Create semantics must also have reliable observed sources; do not infer them from zero IDs.
3. The trusted server must bind that result to the same instance/session token observed at step 2. Compare all identity fields and token before normalizing. Server-local instance UUIDs may not be available inside Luau; do not invent a Roblox API or put the expected UUID into the returned table.

Same-read place fields improve continuity but cannot distinguish two local `Place1` documents with identical zero IDs/user/creator. Re-reading state afterward does not solve an A→B→A switch or wrong routing. A generated/echoed client nonce proves neither origin nor stable session. Reading an existing independently available DataModel identity could be considered only with documented lifetime/security and verified transport binding; creating an attribute/token/Instance is prohibited.

**Continuity guarantee today: none across the separate reads.** Only equality against a synthetic state payload and structural consistency are tested. The available tool contracts do not establish a trusted same-read session binding. This is a **blocker**, not an assumption that C2B execution can investigate automatically. C2B discovery/state observations may reveal whether relevant metadata exists; if they do not, stop and require a separately reviewed server contract/capability change. No technical blocker is waived by human approval.
